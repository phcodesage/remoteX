# Python Remote

An attended remote-support foundation built with Python, FastAPI, PySide6, and WebRTC.

The first slice is intentionally small and visible:

`pairing → local approval → screen streaming → mouse control → revoke`

The agent never opens an inbound listening port. It keeps an outbound WebSocket to the control server. Screen video and control messages use a WebRTC peer connection after the server has exchanged the offer and answer.

## Run locally

```bash
./setup.sh
cp .env.example .env
.venv/bin/python run.py
```

The repository uses one project-local virtual environment at `.venv`. It is ignored by Git because its native packages are platform-specific; `./setup.sh` creates or repairs it on each computer.

The setup pins the compatible PyAV 17 line and requires its prebuilt wheel. This avoids the PyAV 12 Cython build failure that can occur on Python 3.13.

`.venv/bin/python run.py` is the normal one-command startup. It opens the unified desktop UI and automatically starts the local FastAPI server when `REMOTE_SERVER_URL` is localhost. Use `.venv/bin/python run.py doctor` for diagnostics or `.venv/bin/python run.py server` when running the server as a separate service.

After setup, every role can be launched through the same environment:

```bash
.venv/bin/python run.py
.venv/bin/python run.py server
.venv/bin/python run.py doctor
```

Alternatively, activate the same environment first with `source .venv/bin/activate` and then use `python run.py`.

The prototype has no sign-in or sign-up screen. With `REMOTE_LOCAL_AUTH_ENABLED=true`, a localhost server creates a local session automatically. For a shared/external server, put an existing access token in `REMOTE_ACCESS_TOKEN`; the desktop UI still stays single-screen and does not show auth forms.

For external/shared auth, create a user token with:

```bash
curl -s http://127.0.0.1:8000/api/v1/auth/register \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"change-me-now"}'
```

Copy the returned `access_token` into `REMOTE_ACCESS_TOKEN` only when using a shared server:

```bash
.venv/bin/python run.py
```

`.venv/bin/python run.py agent` opens the exact same UI. Each computer can therefore be both a controller and a remote device:

```bash
.venv/bin/python run.py agent
```

The agent shows an in-app attended approval dialog. Only after approval does the viewer create the WebRTC offer and the screen/control session become active.

## Cloudflare networking

`REMOTE_SERVER_URL` can point at the HTTPS hostname exposed by Cloudflare Tunnel. The tunnel carries the FastAPI HTTP and WebSocket control traffic.

WebRTC media needs ICE servers. The preferred setup gives FastAPI a Cloudflare Realtime TURN key ID and API token:

```dotenv
REMOTE_CLOUDFLARE_TURN_KEY_ID=...
REMOTE_CLOUDFLARE_TURN_API_TOKEN=...
REMOTE_CLOUDFLARE_TURN_TTL_SECONDS=3600
```

The current `.env` is already configured to use Cloudflare TURN; credentials are generated by FastAPI when the ICE endpoint is requested.

FastAPI generates short-lived credentials and publishes the resulting ICE server list at `/api/v1/config/ice`. Static `REMOTE_TURN_URLS`, `REMOTE_TURN_USERNAME`, and `REMOTE_TURN_CREDENTIAL` values remain available as a local fallback. Cloudflare Tunnel and TURN are separate paths: the former reaches FastAPI, while the latter relays peer traffic when direct ICE connectivity fails. Do not commit TURN keys or credentials.

## Layout

```text
common/       Shared messages, enums, and hashes
server/       FastAPI auth, device/session APIs, and signaling relay
agent/        Device identity, approval, MSS capture, WebRTC, PyAutoGUI
viewer/       PySide6 dashboard, dark theme, session window, WebRTC client
tests/        Protocol and server lifecycle tests
deployment/   Reverse proxy and Cloudflare TURN notes
```

## Security boundaries in this MVP

- Passwords use Argon2id through `argon2-cffi`.
- Device tokens are stored server-side only as SHA-256 hashes.
- Devices have an Ed25519 identity key stored locally.
- Pairing requests expire and are shown to the remote user.
- The remote user must explicitly allow every attended session.
- WebRTC signaling uses a two-minute, session-scoped token.
- There is no hidden startup, silent enrollment, or unauthenticated inbound agent port.

Before production use, add refresh-token rotation, MFA, rate limiting, structured audit retention, key rotation, Redis for multi-instance presence, and a persistent tray indicator for each supported OS.
